本次对 Helply（公网地址 https://helply.work，本地代码库和数据库）做了一次授权的安全评估和渗透测试，范围包括代码审查、87 项自动化攻击测试、对线上站点的被动探测、对真实数据库的只读审计和依赖状态检查。

## 1.2 最需要先处理的三件事

- **F-01 共享初始密码：** 85 个员工账号至今仍在用同一个初始密码，96 个账号从未登录过。任何知道这个密码的人都能以任何员工身份登录并查看其工单。管理员和技术员账号没有使用它。
- **F-02 登录没有防暴力破解：** 连续输入 30 次错误密码后，正确密码仍然能登录。登录页和 Admin 登录页都开放在公网，且 Admin 唯一的超级用户没有二次验证。
- **F-03 Admin 暴露在公网：** /admin/ 使用默认路径，任何人都能打开登录页。建议用 Cloudflare Access 把它限制在你们团队的邮箱，同时顺带获得二次验证。

这三项都可以在不改业务逻辑的情况下用配置或很小的代码改动解决，第 7 章给出了排期。

## 1.3 做得好的地方

- 访问控制按行级过滤：员工只能看到自己的工单和设备，技术员只能看到本组工单，管理员页面对其他角色一律返回 403 或 404。
- 所有输出都经过转义，包括工单、评论、部门、团队、用户名、服务器名和知识库文章，没有可执行的脚本被注入。
- 所有写操作都要求 CSRF 令牌，只有监控 agent 的上报接口豁免，且它要求有效的 Bearer 令牌。
- agent 令牌有 256 位随机性，数据库里只存哈希，上报内容经过范围校验，超大请求和畸形数据都被拒绝。
- 密码使用 PBKDF2 哈希，重置链接一次有效，伪造 Host 头无法改变重置邮件里的链接，密码重置不泄露账号是否存在。
- 没有发现敏感文件被公网访问（.env、数据库、备份、日志、.git 全部 404），Git 历史里没有密钥。
- Cookie 带有 Secure、HttpOnly（会话）和 SameSite=Lax，生产环境关闭了 DEBUG，404 页面不泄露内部信息。

# 5. 详细发现

## 5.1 F-01 85 个账号共用同一个初始密码（高）

**位置：** 真实数据库中的用户账号，初始密码来自 .env 的 HELPLY_DEMO_PASSWORD。

**证据：** 对真实数据库做只读审计，在 101 个账号中，有 85 个账号的密码仍然与这个共享初始密码匹配，全部是员工角色；96 个账号从未登录过。管理员和技术员账号没有使用它。所有账号使用 PBKDF2-SHA256 哈希，这是好的。

**影响：** 任何知道这个密码的人（团队成员、曾经看到过它的人）都可以登录任意一个还没改密码的员工账号，读取该员工的工单、设备信息，并以其名义提交工单和评论。账号的用户名规则是名字小写，容易猜到。

**建议：**
- 给账号加「首次登录必须修改密码」：在 User 上加一个标记，登录后重定向到改密码页，改完才能使用。
- 对真实员工，改用你们已经做好的一次性设置密码链接（People 页的 Make password link），不再使用共享初始密码。
- 员工都改完密码之后，从 .env 删除 HELPLY_DEMO_PASSWORD，并确认再没有账号匹配它。

## 5.2 F-02 登录没有防暴力破解（高）

**位置：** /accounts/login/ 和 /admin/login/。

**证据：** 在本地临时实例上，对同一个账号连续提交 30 次错误密码，没有任何锁定、延迟或验证码，随后正确密码仍然登录成功（HTTP 302）。代码里没有限速组件，Django 默认也没有。线上是否有 Cloudflare 速率限制规则，无法从外部确认。

**影响：** 攻击者可以对用户名做在线猜密码。风险最高的是 Admin 登录页，因为它对应唯一的超级用户 alice，而且没有二次验证。已知用户名是公开推断的（名字小写）。

**建议：**
- 在应用层加登录限速：同一账号加同一 IP 连续失败 5 次后锁定 15 分钟，可以用 django-axes，也可以自己用缓存实现；记录失败日志。
- 在 Cloudflare 加速率限制规则：对 /accounts/login/ 和 /admin/login/ 的 POST，每个 IP 每分钟不超过 10 次。
- 如果访问量允许，加 Cloudflare Turnstile 验证码。

## 5.3 F-03 Admin 暴露在公网默认路径（中）

**位置：** https://helply.work/admin/login/ 返回 200。

**证据：** 线上探测显示任何人都可以打开 Admin 登录页，路径是 Django 默认的 /admin/。Admin 里能管理所有数据，且没有二次验证。

**影响：** 与 F-02 叠加，让 Admin 成为最有价值的暴力破解目标。Admin 的大部分功能已经迁入主站，真正必须用它的只剩资产、知识库和分类。

**建议：**
- 用 Cloudflare Access 保护 /admin/*：只允许你们几个人的邮箱，认证时自带一次性验证码，等于获得二次验证，不需要改代码。
- 或者把 Admin 路径改成不可猜的路径，作为次要手段。
- 等剩余功能迁入主站后，只让 Admin 在本机（127.0.0.1）可访问。

## 5.4 F-04 重置密码接口没有限速（中）

**位置：** /accounts/password_reset/。

**证据：** 在本地实例上对同一个邮箱连续提交 10 次，短时间内排队了 11 封重置邮件，没有任何限速。

**影响：** 攻击者可以用它给任意员工邮箱刷邮件。对 Helply 来说有两个后果：@helply.work 地址会转发到真实邮箱，会淹没收件人；Brevo 免费套餐每天约 300 封，被耗尽后真实的通知和告警邮件也发不出去，还会损伤发信域名的声誉。

**测试中的积极结果：** 重置接口不泄露账号是否存在，伪造 Host 头无法篡改邮件里的链接（请求被 ALLOWED_HOSTS 拦下），重置链接用过一次就失效。

**建议：** 按 IP 和按邮箱各做限速（例如每个邮箱每小时 3 封，每个 IP 每小时 10 次），在 Cloudflare 规则里也限一下这个路径。

## 5.5 F-05 密钥、数据库和备份对本机所有用户可读（中）

**位置：** .env、db.sqlite3、demo-passwords.txt、backups/ 目录。

**证据：** 文件权限检查显示 BUILTIN\Users 对这些文件有「读取和执行」权限，也就是这台服务器上的任何本地账号都能读。.env 里有 SMTP 密钥、隧道令牌和共享初始密码；数据库里有全部工单和账号；demo-passwords.txt 是明文密码列表。这些文件都没有被提交到 Git，也没有被公网访问到。

**影响：** 现在是你自己的机器，风险有限。迁移到学校的共享服务器后，其他有登录权限的人（包括其他项目的同学）可以直接读取这些文件。

**建议：** 只允许管理员和运行 Helply 的服务账号访问，例如对 .env 执行命令 icacls .env /inheritance:r /grant:r Administrators:F SYSTEM:F 。
对 db.sqlite3、demo-passwords.txt 和 backups 做同样处理。迁移前确认备份目录也不在共享位置。

## 5.6 F-06 边缘节点接受 TLS 1.0 和 1.1（中）

**位置：** helply.work 的 443 端口（Cloudflare）。

**证据：** 用 .NET 的 TLS 客户端分别指定协议版本握手，TLS 1.0、1.1、1.2、1.3 都成功。证书是 Let's Encrypt 签发，到期时间 2026-12-30，由 Cloudflare 自动续期。

**影响：** TLS 1.0 和 1.1 已经被行业淘汰，存在已知弱点；只有很老的客户端才会用到。这需要在 Cloudflare 后台核对，因为我无法登录后台确认设置。

**建议：** 在 Cloudflare 的 SSL/TLS → Edge Certificates 里把 Minimum TLS Version 设为 1.2，并确认 TLS 1.3 已开启，Always Use HTTPS 已开启。

## 5.7 F-07 未经启动脚本启动时默认进入开发模式（低）

**位置：** config/settings.py。

**证据：** 真实 .env 里没有设置 HELPLY_ENVIRONMENT，默认值是 development，这会打开 DEBUG，使用固定的开发密钥。线上站点由 start-online.bat 启动，它会把环境设为 demo、关闭 DEBUG 并生成随机密钥，所以线上不受影响（线上 404 页面不泄露信息）。另外，安全设置（Secure Cookie、HTTPS 跳转、HSTS）只在设置了公网域名时才打开。

**影响：** 如果有人用 manage.py runserver 或别的方式直接启动，而且端口被暴露，会出现调试页面和可预测的密钥。

**建议：** 默认改为 DEBUG 关闭；把「development」改成需要显式设置才能进入；让 start-demo.bat 之外的启动方式在没有显式开发标记时拒绝使用开发密钥。

## 5.8 F-08 没有 CSP，HSTS 只有 1 小时（低）

**证据：** 线上响应头有 X-Content-Type-Options: nosniff、X-Frame-Options: DENY、Referrer-Policy: same-origin、Cross-Origin-Opener-Policy: same-origin 和 Strict-Transport-Security: max-age=3600，但没有 Content-Security-Policy 和 Permissions-Policy。HSTS 的 3600 秒是刻意缩短的，不含子域名也没有 preload。CSRF Cookie 有效期是一年（Django 默认）。

**影响：** 没有 CSP 时，一旦将来出现 XSS，浏览器没有第二道防线；当前测试没有发现 XSS。HSTS 太短意味着降级攻击的窗口更大。

**建议：** 域名稳定后把 HSTS 提高到至少 6 个月；逐步引入 CSP（先用 Report-Only 模式观察，前端是原生 JS 和自有 CSS，没有第三方脚本，比较容易落地）；加一个限制摄像头、麦克风和定位的 Permissions-Policy。

## 5.9 F-09 会话 14 天有效，没有空闲超时（低）

**证据：** SESSION_COOKIE_AGE 为 1209600 秒（14 天），关闭浏览器不会过期。

**影响：** 在共享电脑或设备丢失的情况下，会话会长时间有效。管理员权限的会话尤其敏感。

**建议：** 把会话缩短到 8 到 12 小时，或加空闲超时（例如 30 分钟无操作），对管理员更严。

## 5.10 F-10 agent 分发缺少完整性校验（低）

**位置：** agent/install.sh、agent/install.ps1。

**证据：** 安装命令是 curl ... | sudo bash -s -- --url ... --token ...，agent 和安装脚本都从 Helply 自己下载，没有校验和或签名；令牌通过命令行参数传入，会出现在进程列表和 shell 历史里。agent 本身做得很好：只读、不接受命令、始终校验 HTTPS 证书、拒绝非 HTTPS 地址、配置文件权限 640。

**影响：** 如果 Helply 服务器被攻破，攻击者可以替换 agent，让新安装的服务器执行恶意代码（安装脚本以 root 运行）。令牌短时间出现在命令行里，属于低风险。

**建议：** 在安装页面同时显示 agent 的 SHA-256，安装脚本下载后校验；令牌改为交互输入或从环境变量读取（脚本已经支持交互输入）；长期可以对发布的 agent 做签名。

## 5.11 F-11 相似工单查询未按可见范围过滤（低）

**位置：** apps/ai/services.py 的 similar_tickets。

**证据：** 代码审查发现，技术员打开工单时看到的「相似已解决工单」来自全部已解决和已关闭的工单，没有按技术员可见的范围过滤。在演示数据上做的测试没有复现（20 张工单的相似建议全部是该技术员能打开的），因为同一分类的工单通常属于同一个支持团队。

**影响：** 如果工单被重新分类到别的团队，技术员可能在建议里看到自己团队之外的工单标题和编号（点开会 404）。工单标题可能包含敏感信息。

**建议：** 候选池改用 visible_tickets(user) 过滤。

## 5.12 F-12 已登录用户的创建类操作没有速率限制（低）

**证据：** 提交工单、评论、知识库投票和建议、通知设置都没有速率限制，一个有效账号可以在短时间内提交大量内容。

**影响：** 账号被盗用或内部滥用时，可以制造大量工单，触发 AI 分类、分派和通知邮件，造成骚扰和邮件配额消耗。

**建议：** 对创建工单和评论加简单的限速（例如每个用户每分钟 10 次）；通知邮件已有按「工单加类型」的节流，保留。

## 5.13 F-13 公网启动脚本每次重新生成密钥（低）

**位置：** start-online.bat。

**证据：** 脚本每次启动都生成新的随机 DJANGO_SECRET_KEY。

**影响：** 这不是漏洞，但每次重启都会让所有用户的会话失效，也会让已经发出的一次性设置密码链接和重置链接全部作废，用户体验和运维可靠性受影响。如果以后改成多进程部署，还会让会话互相无法识别。

**建议：** 把一个固定的强密钥放进 .env（start-production.bat 本来就要求这样），启动脚本只在没有设置时才生成。

# 8. 复测与残余风险

- 修复第一周的四项后，建议重新运行测试脚本（87 项）和线上探测，预期 AUTH-01 和 CFG-05 转为通过。
- 迁移到学校服务器后需要重新评估：文件权限、共享主机上的其他用户、防火墙、是否仍通过 Cloudflare Tunnel 访问。
- 切换到生产模式（HELPLY_ENVIRONMENT=production）后，需要复核 Secure Cookie、HTTPS 跳转和 HSTS 是否生效。
- 本报告没有覆盖：对真实 VPS 上运行的 agent 的测试、Cloudflare 和 Brevo 账号本身的安全设置（建议两个账号都开启二次验证）、社会工程和物理安全。
- 排查过程中，一个工具输出里曾出现过 Brevo 的 SMTP 密钥。虽然没有写入任何文件，仍建议在 Brevo 重新生成密钥，并更新 .env。
